Couro vs Vicon — bilateral ankle update

v7 · 2026-05-27 · incremental update to v6 · adds bilateral feature pool + multi-signal event detection for ankle

Deploy count went from 19 → 20. Front-center ankle, which was "do not ship" in v6 (r = −0.37), is now deployable (r = +0.15) thanks to bilateral features + hip-vertical fallback for impact detection.

What changed. Two refinements that we tried in v7:

  1. View-aware foot-side switch — picked the "far foot" per camera. Didn't work — far foot is smaller in pixels and not necessarily cleaner.
  2. Bilateral feature pool — feed both feet's event-anchored features and let ridge learn the weighting. Plus fall back to hip-center vertical for impact detection when ankle detection fails. Worked — side-left and front-center ankle both improved.

Hard limit still in place. Right-side cameras (Cam3 front_oblique_right, Cam4 side_right) for ankle stay unsolved. The structural cause is keypoint quality from those angles — needs either multi-camera fusion or higher-resolution foot keypoints to fix.

2. What "bilateral feature pool" means

v5 fed the ankle regression event-anchored features from the right ankle only. v7 feeds 13 features covering both ankles and both knees/hips, and ridge regression learns which to weight per view:

FEATURE_POOL = (
  "ankle_r_rom_full",        # baseline — full-trial right ankle ROM
  "ankle_r_at_contact",      # right ankle at impact
  "ankle_r_rom_loading",     # right ankle ROM during loading
  "ankle_r_min_loading",
  "ankle_l_at_contact",      # NEW — left ankle features as proxy
  "ankle_l_rom_loading",
  "ankle_l_min_loading",
  "knee_r_at_contact",       # coupled knee at impact
  "knee_r_rom_loading",
  "knee_l_at_contact",       # NEW — contralateral coupling
  "hip_r_at_contact",
  "hip_l_at_contact",
  "loading_duration_frames",
)

Plus the event detector now tries multiple signals in order: right-ankle vertical → left-ankle vertical → hip-center vertical. This rescued Cam2 (front-center), where right-ankle detection was failing on ~80% of trials. With the fallback, only 8 of 54 trials still fail event detection.

5. The view-aware experiment that didn't work (and why)

Hypothesis: right-ankle keypoint is occluded on right-side cameras, so for Cam3/Cam4 use the left ankle (the "far foot") as the measurement source instead.

Result: front_oblique_right ankle r went from −0.21 to −0.44 — worse. side_right went from −0.10 to −0.03 — barely changed.

Why it failed: the "far foot" on a side camera is smaller in pixels (1/distance² in image area), so the keypoint estimate is also noisy — just for a different reason. Sub-pixel localization error in a small region maps to bigger angle error in 2D-to-3D recovery. Bilateral features dodge this trade-off by letting the regression weight both signals jointly.

6. Where the remaining ceiling sits

Three of four still-broken ankle views are on right-side cameras. The bilateral approach exhausted what's recoverable from monocular keypoints on those angles. The next moves all require non-trivial engineering:

  1. Multi-camera fusion at inference (~1 month). Triangulate ankle keypoint in 3D when 2+ camera angles are available. This is the standard biomech-CV unlock and would push ankle into deploy territory across all views. Already maps cleanly onto the Couro 2-camera softball setup.
  2. Foot-orientation prior (~1 week). Use the constraint that the foot is approximately flat on the ground during the loading phase as a soft constraint in 3D recovery. Helps Cam3/Cam4 specifically since the foot is foreshortened from those angles but its orientation can be inferred from temporal context.
  3. Higher-resolution keypoints from sports-specific model. RTMPose-X Halpe-26 has noisy foot/heel keypoints. A specialized sports-pose model trained on athletic data with explicit foot/ankle supervision would lift the ceiling — but that's a real ML project, not a config change.
