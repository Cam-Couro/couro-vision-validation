Couro vs Vicon — ankle event-anchoring update

v5 · 2026-05-27 · OpenCap LabValidation drop jumps · LOSO cross-validated · borrows Couro's existing gait_analyzer event-detection recipe

Ankle is partially recoverable. v4 left ankle dorsiflexion as "do not deploy" — LOSO Pearson r was negative on all 5 camera views. By anchoring features to the detected drop-jump impact event (same technique Couro's gait_analyzer.py uses for sprint touchdown), r flipped from negative to positive on 3 of 5 views.

Headline numbers. Side-left ankle: 9.35° → 7.57° RMSE, r −0.17 → +0.25. Front-center ankle: 13.16° → 7.79°, r −0.37 → +0.19.

Honest correction to v4. v4 claimed the hip-adduction wraparound bug existed in production. It does not — production uses arccos (returns 0–180°, no wraparound). The bug was in our harness file only. Already patched there.

Still unsolved. Right-side cameras (Cam3, Cam4) for ankle. Likely cause: right-ankle keypoint is occluded / foreshortened when the camera is on the right side of the box. Possible fix is view-aware foot-side selection — not yet implemented.

1. What changed: event-anchored features

v4 fed the ankle regression a single ROM number per trial — max minus min across the whole clip. That measurement is dominated by airborne ankle motion (toes pointed in flight, foot relaxed) which has nothing to do with the loading-phase ankle bend that matters biomechanically.

v5 detects the drop-jump impact event from the ankle vertical trajectory (scipy.signal.find_peaks + Gaussian/Savgol smoothing — borrowed directly from app/services/ecs/track_mode/utils/gait_analyzer.py), then extracts features only from the loading window (initial contact → pushoff, typically 100–230ms):

FeatureWhat it captures
ankle_rom_loadingAnkle ROM during ground-contact phase (replaces full-trial ROM as primary signal)
ankle_at_contactAnkle angle the instant the foot lands
ankle_min_loadingDeepest dorsiflexion during loading
knee_at_contactCoupled knee angle at contact (drives ankle position)
knee_rom_loadingCoupled knee ROM in loading window
hip_at_contactCoupled hip angle at contact
loading_duration_framesGround-contact duration (drop strategy indicator)

Event detection succeeded on 207 of 216 trials (~96%). 9 front-center trials skipped because the ankle came to rest mid-window (no clean pushoff event).

Pattern in the failures. Both unsolved cameras are on the right side of the subject (where the right ankle — the one we're measuring — is the near foot and gets foreshortened or occluded by the box edge). Side-left and front-oblique-left work because the right ankle is the far foot and projects more cleanly. Likely fix: when measuring right-ankle metrics, pick a camera on the subject's left (and vice versa). This is "view-aware foot-side selection" and would be a small addition to views.py + the metric registration logic.

3. Honest correction on the hip-adduction "bug" from v4

v4 said: "patch the hip-adduction wraparound bug in production — couro_keypoints.py's arctan2-based 2D proxy needs np.unwrap."

Correction: the file couro_keypoints.py in the validation harness has this bug, but production couro-vision does not. Production's _calculate_hip_adduction in phase_specific_metrics.py uses arccos(dot/mag), which always returns 0–180° and has no wraparound discontinuity. Production also reports peak hip adduction within a detected phase, not max-minus-min across the whole trial, which sidesteps the issue entirely.

Net: the harness patch was needed for the benchmarking only. No production PR required for this. Sorry for the false alarm in v4.

5. How to use the ankle model in production

Coefficients live at results/ankle_event_anchored_models.json. Same JSON schema as the other regression models. The extra requirement vs the simpler v4 models: the event-detection module needs to run before feature extraction.

Reusable from Couro's existing code:

  • app/services/ecs/track_mode/utils/gait_analyzer.py already has the scipy smoothing + peak detection pattern — borrow _detect_events_two_signal's setup directly
  • For DJ (single-impact), the simplified detector in harness/dj_events.py is ~120 lines and pure scipy. Drop-in to metrics_calculator/utils/ and use from a new AnkleDorsiflexionMetric class

Inference flow:

1. detect_dj_events(ankle_y_pixels, fps) → returns (initial_contact_frame, pushoff_frame)
2. extract event-anchored features from the [IC, pushoff] window
3. z = (raw - feature_mean) / feature_std
4. predicted_ankle_rom_deg = z @ weights_zscored + intercept

6. Where to push precision higher (open questions)

  1. View-aware foot-side selection for Cam3/4 ankle. Quick implementation, would extend ankle coverage from 2 → 4 views.
  2. Foot vector from midpoint(big_toe, small_toe) − heel instead of heel → big_toe. Averaging two keypoints cuts noise √2×. Worth ~½ day to test.
  3. Apply event-anchoring to all other metrics too — likely lifts hip_flexion_r front_center (currently scale-only at r=0.23) and knee_angle_r front_center (currently r=0.15) into properly deploy-ready territory.
  4. Add nonlinear regression (gradient boosting) on the same features. Ridge is linear; some couplings (e.g. hip-knee-ankle phase relationships) are not. With 54 trials × 9 subjects, careful regularization needed but worth trying.
  5. More training data remains the dominant ceiling — current ~54 trials × 9 subjects per view limits what any model can learn. Plausible expansions: AthletePose3D (Waseda, commercial license needed), in-house mocap data collection, OpenCap field-study sub-license.
