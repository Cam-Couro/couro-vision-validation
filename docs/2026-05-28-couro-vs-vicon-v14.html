3. Why DWPose helped ankle specifically — the mechanism

Ankle dorsiflexion is the only metric that requires foot keypoints at both the feature side (to compute the angle from video) and the GT side (to compute the angle from mocap). RTMPose-X Halpe-26 has feet as 6 of 26 outputs — a thin slice of training supervision. DWPose-L UCoco-384 has feet as part of a 133-keypoint COCO-WholeBody distillation with explicit foot heatmap teaching.

For v12 and v13, the OpenCap ankle features came from RTMPose. The model couldn't learn to map RTMPose's noisy foot positions to the precise mocap ankle dorsiflexion angles. For v14, OpenCap features come from DWPose — the foot positions are tighter, the angle estimates are more consistent, the regression finally has a signal to fit.

This also explains why DWPose didn't help front-center hip/knee in v13: those metrics don't need feet. They got slightly worse because DWPose spreads model capacity across face+hands+feet vs RTMPose-X being a body specialist. For ankle, that tradeoff inverts.

5.4 Production deploy plan — concrete steps

  1. Bundle DWPose-L ONNX with the existing model package (`models/prod/`). 128MB delta. The remapping layer is 50 lines of Python (already in aspset_infer_dwpose_gpu.py).
  2. Update the routing layer (rtm_pose_inference.core.inference_engine) to also load a DWPose session at startup. Add a _dwpose_session alongside _rtmpose_session.
  3. Per-frame inference chooses one or both backbones based on the requested metrics. For ankle ROM or any side-view metric → DWPose. For front-view hip/knee → RTMPose. For all-metric → both.
  4. The 25 ridge models (deploy_ready_models.json) get loaded into memory at startup; the per-slot picker is just a dictionary lookup at inference. Total model weight memory: ~50KB.
  5. The view classifier already exists (in views.py) — no change needed.

10. What's still left as a real lever

  1. Close ankle × front_oblique_right. Sport-specific videos with deliberate camera angles + foot-occlusion-aware training would address the last scale-only slot. ROI: this is the smallest remaining slot — not worth a major data collection by itself, but free if it rides along with sport-specific data work for softball/hockey.
  2. Sport-specific validation — AUSL softball pitching, Sharks hockey skating still need their own validation data. ASPset is generic athletic motion; sport-specific pose distributions will move the front_center metrics that didn't lift this round.
  3. Mobile/on-device deployment — quantize both backbones to INT8 or CoreML. Both have the same SimCC architecture so quantization tooling transfers. Existing Couro RTMPose mobile inference path is the template.
  4. Multi-camera fusion — still out of scope for product constraints, but would push best r toward 0.90+.
