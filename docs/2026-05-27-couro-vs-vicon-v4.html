Couro vs Vicon — multi-metric regression brief

v4 · 2026-05-27 · OpenCap LabValidation drop jumps · 9 subjects · 270 video trials · LOSO cross-validated

Recipe extended. v3 showed the biomech regression trick recovers hip-flexion from front view (48° → 21° RMSE, −55%). This brief applies the same pattern to four more metrics.

Headline. 5 metrics × 5 camera buckets = 25 trained models. 15 deploy-ready (RMSE down, Pearson r positive in LOSO). 5 partial (RMSE down but r low — scale corrector only). 5 do-not-deploy (ankle dorsiflexion across all views).

Honest limitation. Ankle ROM from 2D Couro keypoints is unrecoverable with this feature set — LOSO Pearson r goes negative on every view. Foot/heel keypoint noise + small joint excursion + camera-frame foreshortening means no monotonic mapping exists.

Output. results/all_metrics_regression_models.json — same schema as the v3 hip-flex file, ready for drop-in to metrics_calculator/ alongside knee_rotation.py.

1. What's new since v3

v3 trained one regression (hip_flexion_r) and validated against Vicon mocap. v4 generalises the pipeline: a 13-feature pool extracted once per trial, then a per-(metric × camera-view) ridge regression trained on a metric-specific subset of those features.

Four new target metrics — chosen because they're already calculated by Couro's metrics_calculator and they have OpenSim GT in every trial:

3. How to read these numbers

Two metrics matter, and they tell different stories:

  • RMSE drop (Δ%) — by how much the average error shrinks. Big drops mean the regression's scale matches Vicon better than the raw 2D estimate. This is what you want for "in degrees, how off are we typically."
  • Pearson r (LOSO) — whether per-trial variation is preserved. A model can have low RMSE but low r if it just predicts the population mean for everyone. A model needs both to be useful at the individual level.

"Scale only" verdicts are honest about the limitation: those models give a reasonable population estimate but can't distinguish a deep squatter from a shallow one. For Couro's use case (coaching individuals, week-over-week deltas), only the deploy rows are reliable for showing change.

5. Integration handoff

The trained coefficients live at:

multiview-validation/results/all_metrics_regression_models.json

Same schema as the existing knee_rotation.py coefficients in metrics_calculator/metrics/. Each (metric × view) entry has:

{
  "camera_id": "Cam2",
  "view_bucket": "front_center",
  "target_metric": "knee_angle_r",
  "feature_names": [...],
  "feature_mean": [...],
  "feature_std":  [...],
  "weights_zscored": [...],
  "intercept": ...,
  "loso_cv_stats": {"rmse_deg":..., "pearson_r":..., ...},
  "naive_baseline": {"rmse":..., "pearson_r":...},
  "rmse_reduction_pct": ...
}

Apply with the same recipe Saad already uses for knee rotation:

z = (raw_features - feature_mean) / feature_std
predicted_rom_deg = z @ weights_zscored + intercept

View-bucket selection should match the camera-yaw classifier already used by Couro's existing pipeline (harness/views.py in this repo mirrors the same conventions).

6. Recommended next steps

  1. Ship knee_angle_r, lumbar_extension, hip_flexion_r side_left — biggest, most reliable wins. Wire into metrics_calculator as new MetricCalculator subclasses following the knee_rotation.py pattern.
  2. Patch the hip_adduction wraparound bug in production — couro_keypoints.py's arctan2-based 2D proxy needs np.unwrap applied before ROM. Quick fix, big impact on the raw metric even without the regression.
  3. Hold ankle until we have either: (a) higher-confidence foot keypoints, or (b) a richer feature set (heel-strike timing, foot-progression angle, multi-frame temporal context).
  4. Validate on AthletePose3D when commercial license sorted — current models are trained on n=54 trials from 9 subjects (drop-jumps only). Generalization to softball pitching / hockey / basketball motions is unverified.
